# Устойчивость и жизненный цикл

## Владение данными

Сервер + пользователь определяют владельца каталога, очереди, обложек, загрузок и отложенных
отметок. Одинаковый song ID на разных серверах не объединяет записи. Каталог и очередь
продолжают работать без сети. Ошибка необязательной полки не стирает сохранённые данные.

Старые загрузки Android/desktop без владельца остаются на месте и показываются как локальная
музыка. Они не скробблятся от нового аккаунта. Старые pending-scrobbles без владельца не удаляются
и не отправляются автоматически: их сервер нельзя надёжно восстановить из старого формата.

## Прослушивание

Сеанс: account, songId, playId, startedAt в миллисекундах эпохи, submitted. Пауза, повтор
сетевой попытки и восстановление очереди продолжают тот же сеанс. Новое воспроизведение/повтор
создаёт новый playId. Порог общий: длительность >30 секунд, позиция >=min(половина, 240 секунд).
Сначала сохраняется pending-запись, затем снимок с submitted. Повторная постановка одного playId
безопасна. Успешные записи удаляются по одной, остальные сохраняются.

Если сервер обработал запрос, а ответ потерялся, клиент не может доказать доставку: полная
серверная дедупликация требует поддержки сервера. Локальная дедупликация не обещает exactly-once
доставку через произвольный Subsonic-сервер.

## Загрузки

Задание хранит владельца, Song и качество, но не пароль и не подписанный URL. Восстановление
использует системное хранилище учётных данных. Неудачное задание остаётся для повтора.
Чтение списка не удаляет `.part`, который может записываться в этот момент.
На iOS задачи выполняет background URLSession, Android — foreground dataSync-сервис, desktop —
очередь основного окна (в том числе скрытого). После завершения процесса задания продолжаются
при следующем запуске. Установленные ОС ограничения фоновой работы сохраняют силу.

Подготовка очереди выключена по умолчанию: до 3 серверных треков, до 15 минут, до 256 МиБ
автоматических копий. Только подтверждённое безлимитное соединение; экономия данных/ограниченная
сеть приостанавливают подготовку. Ручные загрузки не вытесняются; на них можно задать общий
лимит места. Сохранение автоматической копии вручную делает её постоянной.

Desktop использует Network.framework на Mac, ConnectionCost на Windows, NetworkManager на Linux.
Если система не сообщает условия соединения, автозагрузка ждёт. Force stop в настройках Android
блокирует сервисы до следующего открытия приложения.

## Проверка

`python3 scripts/verify.py` проверяет ядра и сборки, HTTP против мока и desktop e2e.
`--ios-ui --android-ui` добавляет нативные сценарии на выделенных симуляторах/эмуляторах.
Логи и JSON-отчёт создаются в build/verification. В репозиторий машинные логи не попадают.
Общие сценарии находятся в shared/cases: lifecycle.json, preparation.json, queue.json,
scrobbles.json. Платформенные тесты дополнительно проверяют файловые хранилища, смену подключения
во время запроса и обновления интерфейса от таймера.
