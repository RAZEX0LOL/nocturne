# Общий контракт Nocturne

Приложения написаны на разных языках — Swift (iPhone, iPad, Mac), Kotlin (Android) и TypeScript
(Windows, Linux, macOS), — поэтому код между ними не переиспользуется. Общее здесь другое:
**описание поведения и исполняемые проверки**, одинаковые для всех платформ.

```
shared/
  spec/        — как приложение обязано себя вести
  cases/       — те же правила в виде данных: вход → ожидаемый результат
  fixtures/    — эталонные ответы сервера
  mock-server/ — поддельный Navidrome для ручных и сквозных проверок
```

Эталон — реализация для iOS: она написана первой и обкатана на живом сервере. Кейсы сняты с её
тестов, поэтому новая платформа считается сделанной правильно не тогда, когда «работает у меня»,
а когда проходит те же кейсы.

## Как это используется

Каждая платформа держит маленький раннер, который читает JSON из `cases/` и прогоняет его через
своё ядро:

| Платформа | Раннер | Запуск |
|---|---|---|
| iOS / iPad / Mac | `Tests/NocturneCoreTests/ContractTests.swift` | `swift test` |
| Android | `android/core/src/test/kotlin/.../ContractTest.kt` | `./gradlew -PcoreOnly :core:test` |
| Desktop | `desktop/src/core/contract.test.ts` | `bun test` |

Сейчас в контракте: адрес сервера и учётные данные, сборка запроса, разбор ответов, повторные
попытки, очередь, выравнивание громкости, качество потока по типу сети, очередь отметок о
прослушивании и выбор источника звука.

`cases/source.json` (откуда играть трек: файл, загрузка или поток) исполняют Android и десктоп.
На iPhone это правило пока живёт в слое приложения, а не в ядре, поэтому раннера там нет.

Помимо проверяемых правил в `spec/` лежит `interface.md` — язык интерфейса и оформление: кейсами
это не выразить, но расходиться платформам там тоже нельзя.

Меняешь поведение — правишь сначала `spec/` и `cases/`, потом код платформ. Кейс, который проходит
на одной платформе и падает на другой, означает расхождение в поведении, а не проблему раннера.

## Формат кейсов

Каждый файл — объект с полем `cases`. Внутри — самодостаточные случаи с понятным `name`; раннер
обязан провалить тест с этим именем, чтобы расхождение было видно без чтения JSON.

Пароли в кейсах фиктивные (`test-only`, `sesame` из официального примера Subsonic) и нужны только
для проверки алгоритма подписи.
